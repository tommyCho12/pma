# Document Ingestion Service Integration

## Overview
The document management system integrates with an external ingestion service to process documents for RAG (Retrieval-Augmented Generation) capabilities. This service handles document indexing, embedding generation, and semantic search functionality.

## API Integration Details

### Configuration
- **Service URL**: `INGESTION_SERVICE_URL`
- **Default**: `http://localhost:8001`

## Document Operations

### 1. Adding a New Document
When a new document is created in the system, the ingestion service API is called to index it.

**Endpoint**: `POST {INGESTION_SERVICE_URL}/documents/ingest`

**Request Payload**:
```json
{
  "document": {
    "document_id": "{document id}",
    "title": "{document title}",
    "content": "{document content}"
  }
}
```

**Parameters**:
- `document_id`: Unique identifier for the document that was generated by the document management system
- `title`: Document title/name
- `content`: Full text content of the document

### 2. Updating an Existing Document
When a document is edited or updated, a two-step process is required to ensure the ingestion service has the latest version:

**Step 1 - Delete existing document**:
```
DELETE {INGESTION_SERVICE_URL}/documents/{document id}
```

**Step 2 - Re-ingest updated document**:
```
POST {INGESTION_SERVICE_URL}/documents/ingest
```
With the same payload structure as adding a new document (see above).

**Rationale**: This approach ensures that old embeddings and chunks are completely removed before new ones are generated, preventing stale or duplicate data in the vector database.

### 3. Deleting a Document
When a document is deleted from the system, it must also be removed from the ingestion service.

**Endpoint**: `DELETE {INGESTION_SERVICE_URL}/documents/{document id}`

**Parameters**:
- `{document id}`: The unique identifier of the document to delete

## Implementation Notes

- All API calls to the ingestion service should be made asynchronously to avoid blocking document CRUD operations
- Implement proper error handling and retry logic for network failures
- Consider implementing a message queue or event-driven architecture for better reliability(not for now)
- Log all integration attempts for debugging and monitoring purposes
- Handle cases where the ingestion service is unavailable gracefully (e.g., queue for later processing)
